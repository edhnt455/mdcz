# 单容器运行与通知恢复

MDCz 仍只需要一个 Compose 服务、一个镜像和对外端口 `3838`。容器内由 tini 转发信号并回收孤儿进程，Node 入口负责管理两个子进程，共有三个 Node 进程：

| 进程 | 职责 |
| --- | --- |
| 入口 | 接收 Emby 通知、持久化后应答、转发其他 HTTP 请求、恢复子进程 |
| API | 页面、资源与 SSE；独立连接读取业务数据库；提交操作给 worker |
| worker | 扫描、刮削、删除、整理和媒体写入；独占数据库启动恢复与任务锁 |

内部 HTTP 使用权限受限临时目录里的 Unix socket，不增加 NAS 监听端口。API 的业务数据库连接只读，不运行迁移、任务恢复、目录监听或定时任务。媒体修改和需要执行工作的查询统一转交 worker。任务进度通过 IPC 广播，API 合并 SSE 刷新通知；依赖运行中状态的查询读取最近一次广播。worker 忙碌时进度可能暂时停留，影片库等数据库查询仍可独立服务。

## Emby 通知语义

入口验证凭证和格式后，将通知写入 `MDCZ_DATA_DIR/webhook-inbox.sqlite`；默认 Docker 路径为 `/data/data/webhook-inbox.sqlite`。它与业务数据库分离，使用 WAL、`synchronous=FULL` 和短事务。只有提交成功才返回 `202`，重复通知返回 `200`；落盘失败返回 `503`。`202` 只表示通知已保存，执行结果以删除任务页面为准。

worker 按有界批次转交通知，异常按退避时间重试，随后复用业务删除队列。业务事件和通知回执映射在同一事务提交；若提交后、确认前进程退出，重放会命中原回执。业务层原有的资源版本去重仍然生效，不因不同入口回执而重复创建删除任务。

尚未转交的通知在删除任务页面显示“通知已保存，等待处理”。成功转交后入口清除原始通知正文，已转交回执保留 30 天；未完成的通知不按时间清除。该持久化入口目前覆盖 Emby 删除通知，CloudDrive 与其他自动化接口仍由 worker 处理。

API、worker 异常退出会分别自动恢复，重启退避上限为 30 秒。已接收的 Emby 通知继续转交；已持久化的业务删除和待处理任务沿用现有恢复逻辑。刮削、扫描任务发生进程中断时保留中断状态，需按页面提示重试，不能将自动拉起进程理解为所有媒体任务自动续跑。入口进程重启由 Docker 的 `restart: unless-stopped` 接管。

## 升级、验证与回滚

本次新增迁移 `0020`（查询索引）和 `0021`（通知回执表），不修改已发布迁移。没有新的用户环境变量或外部服务依赖，Compose 的端口、卷和服务数不变。构建产物增加 `chunks/` 目录，必须连同 `server.js`、资源、WebUI 和迁移一起发布，不能只替换单个 JS 文件。

发布前停止旧容器并备份整个 `/data` 挂载目录，确保数据库与 WAL 一致；随后使用新镜像启动原 Compose 服务。检查 `/ready`、页面查询、通知接收，以及日志中的 API、worker PID，再执行受控删除和批量新增验证。只有通过真实 NAS 场景验证后，才能确认生产效果。历史漏单需单独核验和审批补偿，不由升级自动删除。

回滚前停止新容器，检查并记录尚未转交的入口通知；旧版本不会消费新增入口队列。确认这些通知的处置方式后，再切回旧镜像。需要恢复数据时使用升级前的完整备份；恢复备份会丢失其后的任务和媒体记录变化，不能仅复制主数据库文件而忽略 WAL。

本地故障测试会暂停 worker、在数据库锁定时发送通知、终止并恢复 API 和 worker，检查页面查询、SSE、落盘失败响应和去重。测试只使用临时目录，不连接 Emby、MoviePilot 或生产媒体库。
